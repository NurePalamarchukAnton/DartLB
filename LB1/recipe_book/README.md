# recipe_book (ЛР1)

Варіант 13 — рецепти й списки покупок.

## Як запустити

```bash
dart pub get
dart run
dart analyze
```

## Чому така структура

Зробив звичайний console-проєкт через `dart create`. У `bin/` тільки main, уся логіка в `lib/`, щоб потім можна було писати тести і не тягнути все з точки входу.

Файли в `lib/src/` розкидав по сенсу:
- `sample_data` — вхідні рядки і константи
- `parsers` — розбір CSV-рядка
- `validators` — перевірка діапазонів
- `aggregators` — фільтри, середнє, групування
- `report` — текстовий звіт

Класи не використовував, бо в першій лабі так і треба. Дані тримаю в records (`RecipeRecord`, `Ingredient`) — зручніше за Map, і без зайвого ООП.

## Чому такі типи

`parseLine` повертає запис з `recipe` і `error`, щоб не кидати exceptions на криві рядки. Числа паршу через `tryParse`, бо для очікуваної помилки формату це нормальніше ніж try/catch з `parse`.

Для звіту взяв `StringBuffer`, бо склеювати рядки через `+=` у циклі погана ідея. Групування — звичайний `Map` за кухнею. Дати — `DateTime.difference`, як у завданні.

`!`, `late` і `dynamic` ніде не юзав.

## Залежності

З pub.dev по суті майже нічого свого не тягнув.

- `path` — прийшов разом із шаблоном console-проєкту. У цій лабі файлові шляхи не збираю, тож у коді його немає. Можна було б прибрати, але лишив як є з `dart create`.
- `lints` — щоб працював `analysis_options.yaml` з recommended-правилами. Без цього `dart analyze` не той рівень, який просять у методичці. Альтернатива — тільки core-лінти, але recommended звичніший.
- `test` — для парочки перевірок розбору. Поклав у `dev_dependencies`, бо в рантаймі застосунку тести не потрібні.

Решту робить стандартна бібліотека Dart, окремих пакетів для CSV чи колекцій не підключав.
